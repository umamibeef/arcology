.. _enhanced-renderer:

=================
The 2.5D renderer
=================

.. container:: eyebrow

   The enhanced world · built · 1 September 2026

.. container:: lede

   What exists of the enhanced world's renderer, and how to run it. The direction and the decisions behind it are on the :doc:`future` page; the original's own drawing, which this is measured against, is on :doc:`rendering-pipeline`. The software rasteriser, ``arcology --soft``, is checked against the original's frame; the GPU path, ``arcology``, is checked against the software rasteriser.

The composition
---------------

.. rubric:: ``arcology --soft --mesh`` · ``--mesh-reverse``

The software rasteriser draws the frame a second way, selected by ``--mesh``: the terrain first, on its own, and everything else afterwards. The terrain pass paints the skirt columns, the ground tile (terrain, zoned-lot ground or a data-view tint) and the elevated anchor's footprint ground, and writes a depth plane holding the painter's index of the tile that owns each pixel. The sprite pass then draws buildings, networks, traffic, the no-power marker and things in the original's anti-diagonal order, tested against that plane and never writing it. Terrain owned by a tile later in the sweep hides a sprite pixel; sprite-on-sprite order stays the sweep's. The underground view keeps the single sweep, because it emits ground and buried pieces together per tile.

This is the composition rule of the 2.5D renderer: the only depth the original ever had is "drawn later in the sweep", and a depth plane that stores exactly that reproduces the painter's algorithm tile for tile. ``--mesh-reverse`` draws the terrain pass back to front, which must change nothing, since the plane and not the loop carries the ordering.

The rejected count is what proves the test: the plane hid over a million sprite pixels behind nearer terrain at 32 px and the frames still match, so the occlusion the sweep used to do by ordering is now done by depth.

``--provenance`` writes a second plane beside the picture, one 16-bit sample per pixel: the id of the sprite that painted it within its art set, with bit 15 set where the shadow pass darkened it afterwards, and 0 for the background. It is what a check of the terrain mesh reads: every pixel a non-terrain sprite painted must survive the mesh unchanged.

The provenance plane
--------------------

.. rubric:: ``arcology --soft --provenance out.png``

A second plane written beside the picture, one 16-bit sample per pixel: the id of the sprite that painted it within its art set, with bit 15 set where the shadow pass darkened it afterwards, and 0 for the background. It is what a check of the terrain mesh reads: every pixel a non-terrain sprite painted must survive the mesh unchanged. Adding it changed no byte of any existing output, checked on eight renders covering the three zooms, the underground view, a data view, a palette phase, a crop and an indexed export.

The shape table
---------------

.. rubric:: ``python3 tools/terrain_shapes.py`` · ``assets/terrain-shapes.json``

Each of the fourteen slope codes built as faces from its corner mask, projected exactly as the rasteriser projects, and compared against its sprite at all three zooms, for both diagonals. The table it prints is the mesh's geometry; what it found about the art is stated with the slopes on the :doc:`mechanics` page: the far edges that slope down from a raised corner are drawn at three pixels per four rows where the projection gives four per five, and code 13 is drawn as a flat tile raised one level. Code 7 reproduces its sprite only when cut from north-east to south-west; every other code is indifferent to the cut.

Running it
----------

All from the repository root, with the game folder as installed:

.. code-block:: console

   cmake --build build

   CITY="$SC2K_CITIES/Manhattan"
   build/arcology --soft assets "$CITY" plain.png --zoom 32
   build/arcology --soft assets "$CITY" mesh.png  --zoom 32 --mesh
   build/arcology --soft assets "$CITY" rev.png   --zoom 32 --mesh-reverse

All three print the same CRC. The two ``--mesh`` runs also print how many sprite pixels the depth plane hid behind nearer terrain. ``--zoom 16`` or ``8``, ``--view``, ``--phase``, ``--crop`` with ``--scale`` and ``--focus`` combine with ``--mesh``; the underground view keeps the single sweep.

.. code-block:: console

   build/arcology --soft assets "$CITY" out.png --zoom 32 --indexed --provenance prov.png
   build/arcology --soft assets "$CITY" out.png --zoom 32 --mesh --depth depth.png
   python3 tools/terrain_shapes.py

``--depth`` writes the depth plane of a ``--mesh`` render as a 16-bit greyscale PNG, full frame, before any crop: the painter's index of the tile owning each pixel, 0 where no terrain was painted. Under a zone building it is 0, because the original paints no ground there; the only terrain that owns pixels in a built-up district is the ground under networks and the open land and water.

The GPU path
------------

.. rubric:: ``arcology`` · ``r_sweep`` · ``r_gpu.c`` · ``tools/gen_shaders.py``

The software rasteriser's sweep emits an op list, one entry per blit the original makes, in the original's order, and paints it afterwards; ``r_sweep`` is that list as a function. The GPU path uploads the same list as instances and draws it through SDL_GPU: the terrain ops first with depth writes, the sprites after them tested against that depth and never writing it, the shadows into a mask, and a resolve onto the window. The depth is the sweep's painter's index, so the composition is the 2.5D one above. The atlases are uploaded as palette indices and resolved through a 256-entry palette texture that the app rewrites when the animated runs turn, so no pixel is resolved on the CPU. Shaders are authored once in GLSL and embedded as SPIR-V and MSL, so a plain build needs no shader tools.

``arcology --check out.png`` draws one 1280 by 800 frame both ways, the GPU frame and the software frame cropped to the same canvas rectangle, and counts the pixels that agree.

Identical means the same CRC over the raw RGB. The pixels that differ are traffic cars, and they are the one place the GPU path approximates. ``$19004`` paints a car only where the destination still holds the road surface, index 0x91, and a fragment shader cannot read its destination, so the shader tests the road sprite's own texel under the pixel instead. The two agree except where the destination was painted by an earlier tile's op: at 16 px a car's art crosses into the next road tile, and the second car is stencilled against the first car's grey. With moving things left out, all three cities are identical at all three zooms. The shadow of a flying thing is applied in the resolve pass by ``$19B76``'s rule on the index the sprite pass left in alpha, which is exact wherever no later sprite painted a dirt-ramp index under the silhouette.

The terrain as geometry
-----------------------

.. rubric:: ``r_mesh.c`` · ``arcology --terrain3d`` · key ``t``

``r_mesh_build`` follows four rules, listed in the file's header, and nothing else is in it (the user, 2 September 2026: "this is all very inconsistent, seems like your rules are too complicated for what should be simple"). **One ground field.** Every grid corner has one height, the mean of what the land tiles meeting there say: ``ALTM``'s level plus the slope code's corner lifts, read off the sprites by tools/terrain_shapes.py. Land means land: a tile carrying a structure draws its own pad or plane and does not vote, and a corner among structures only takes their mean. Until 2 September 2026 every tile voted, and beside a road on a hillside three pads at a level and one land tile a level up put the corner a quarter up, which tilted the land and left a quarter-level tooth of wall along the road at every such corner, the dark notches at the bends of the user's Barcelona screenshot; now the land keeps its shape and the wall rule closes the whole difference. On 97% of the shipped cities' corners the tiles agree; on the diagonal ramps the mean joins them, and the dark wedge of wall the original's slope sprite shows above a lower neighbour, an artefact of each sprite being drawn alone, is not drawn. Water does not vote: a water tile is flat at its table whatever its low nibble says, so the land around a pond level with its ground stays level with the pond, and a corner no land reaches takes the table there. But a corner that touches water is never below it: the shoreline is at the water. ``ALTM`` keeps one level per tile and the slope code's lifts, and along a shore the land's low corners lie at the bed's level, one below the water they touch, at 725 corners across the 85 shipped cities (73 in Egypt Falls alone, two levels deep at one in St. Christopher). The original never shows them: the water tile's flat diamond at the table, with its sand rim, is painted over them, and the shore reads as level with the water. The mesh, with no diamond to paint over anything, showed a pit at every one, a wedge of earth below the water beside it (the user, on Bay View's column 67, row 124: "tiles dip underground; this is actually replicated in the real game, but it looks ok because there are tiles used that hide this"). Raising those corners to the water they touch is the whole fix; the rest of the tile keeps its heights, so a basin behind the shore stays a basin, as the original shows it. Water is every ``XTER`` from ``0x10`` up: the submerged and shore slopes of a body, and the streams, canals and waterfall from ``0x30`` on, whose table is their level. That is the original's own reading, ``tile_alt`` in the sweep, which places every one of them at the table, flat; the low nibble says where the art puts its rim, not a height. A build that read a stream's nibble as a height, and let it vote, raised Bay View's column 110, row 19, a stream with a slope nibble among flat neighbours, into a bump (the user: "why is 110, 19 raised? that makes no sense"). **Every tile draws one top face**, at the level the original draws its sprite, and one function, ``tile_top``, says which, for both sides of every edge. Plain land and streams draw the field, cut along the diagonal the sprite is cut along: the one that avoids a single odd corner, which keeps a flat triangle on the other three as the sprite of code 7 shows, and NE-SW for the saddle. Water is flat at its table, a waterfall at its own level, the lower one, so the drop at Bay View's dam is a vertical face of water by the wall rule below; averaged with its neighbours it had been a tilted sheet and a hole. A building or any flat network piece is a flat pad at its level: the tile's ground; one step up for a network piece on a saddle, terrain code 13, as the original draws it (``$17528``: ``cmpi.w #$d``, then -12); the water's table for anything standing on water; and its anchor's level across a building's whole footprint, since ``$1716C`` draws no ground under a building and the art is placed by the anchor, the nearest tile of the same building carrying the rotation's corner bit within a four-by-four window to the north-east. A sloped network piece draws its own plane, and the sloped pieces are a fixed set the corpus decided: across every shipped city the power lines ``0x10`` to ``0x13``, roads ``0x1F`` to ``0x22``, rail ``0x2E`` to ``0x31``, highway ``0x3F`` to ``0x42`` and elevated pieces ``0x61`` to ``0x64`` stand on a sloped terrain code every time and every other piece on flat ground, bar a few anomalies such as a road curve on a saddle (Bay View, column 120, row 85). A pad's vertices carry no gradient, so the material shades it as the flat ground it is. **Walls close every difference.** Where two neighbours draw different heights along their common edge, one quad fills the gap between what each draws, done once per edge from the east and south sides: coursed blocks when either tile carries a building, ``XBLD`` from ``0x70`` (the foundation of a plot: the user, "these ramps are all engineered"); a face of water where both are water (the waterfall's drop, a dam's spill); earth otherwise, the bank where land stands above the sea, and the step under a network piece, a road curve lifted on its saddle or a slope piece against a corner the field averages, since the original draws the slope under such a sprite as ground and Bay View's hill road at column 26, row 12, had stood on block walls (the ramp of a raised road keeps its own embankment of blocks, below). The quad may twist where the two edges cross and is still two triangles on the same four points, so every edge it makes is shared. **The water is a body with a floor.** Under every water tile lies the seabed, at the bed field: at a corner that touches water, the mean of the water tiles' own beds there (``ALTM``'s level with the shore code's lifts), never above the surface drawn over it -- an earlier build averaged the land's surface into it, which raised a sand spike through the marina at Bay View's column 118, row 16 -- and the ground elsewhere. On every side of a water tile that is not water, the land goes on below the surface down to the seabed. The map's cut edges, the two far ones or all four when the view turns, show the layers of sediment from what the tile draws down to the base, the foundation of a pad or a ramp as blocks above the ground, and through water the glass from the surface to the seabed with the sediment under it; every layer is measured from the bed field, so the layers are continuous across shorelines and under every foundation. Each face carries its tile's painter's index as depth, a wall its tile's index and a half so it stands between its two tiles, so the sprites compose with the mesh exactly as they do with the terrain sprites; the faces are flat-shaded by a sun fitted to the slope sprites, over a material laid out in world coordinates so it does not swim with the camera, described below: of the four plain slopes at 32 px the one facing south is the brightest, mean luminance 135 against 88 east, 84 north and 71 west, so the light stands to the south-east.

**The mesh is watertight, and a test says so** (the user, 2 September 2026: "any triangle that is drawn must connect to another one, meaning, you shouldn't have any free edges"). ``r_mesh_check`` keys every edge of every triangle on its quantised end points -- heights are means of at most four levels, so forty-eighths are exact -- and counts the triangles on each; an edge with one is free. A vertical edge is a span on its corner's vertical, and the walls meeting at a corner split that vertical differently, so verticals are checked as coverage: every part any edge covers must be covered at least twice. The base of the cut, level zero, is the floor and is closed by definition. ``arcology <assets> <city> --mesh-check`` builds the turned mesh, which cuts all four edges, runs the check, prints the first forty free edges with their tiles and materials and a count by material, and fails on the first; ``ctest`` runs it on Bay View, Cape Wells, Egypt Falls and Felsenschloss, and every one of the 85 shipped cities is closed, 39 to 58 thousand triangles each. One of them, The Bahamas, found a rule short: a marina whose anchor is a land tile one level below the water around it has its pad below the seabed, and the seabed's edge came free; the bed at a corner is now never above the surface drawn over it, the pad included, rather than never above the table. The checker's own test: ``SC2K_CHECK_OPEN=1`` checks the plain build instead, whose two uncut edges are open by design, and it reports them. Because both sides of every edge are measured by the same ``tile_top``, the mesh closes by construction, and the earlier per-case rules -- plinths, wedges, banks, filled bridge approaches, a lookup of the neighbour's corners that was wrong for two of the four edges -- are gone with the cracks they caused. ``SC2K_NO_PLINTH``, ``SC2K_MESH_WALLS`` and ``SC2K_MESH_ROADS`` went with them; ``SC2K_MESH_DUMP=row,col`` remains and prints a tile's kind, corners and bed.

The underground view fills its backdrop white, as the original does (``$15452``), not with the sky. In sprite mode it is the original's: the ground at its own altitude, the seabed under water, the empty tiles' wireframe lattice, the pipes and subways on it, pixel-identical to the software rasteriser. With the mesh on it is the same ground as a mesh, every tile at the ground field and the seabed under water with its slope codes, but only its lattice is drawn: a hairline one device pixel wide at any pixel scale and zoom (the grid's half-width is passed to the shader in canvas pixels, half a device pixel here), every other fragment discarded, so the ground between the lines is the white backdrop and hides nothing. The original's underground ground is a wireframe that hides nothing either: the pipes and subways of the tiles behind show through it, and only a lattice line in front paints over them. A build that drew the ground white with depth had a tile's ground in front covering the subway sprites of the tiles behind, and subways no longer overlapping each other as the painter's order makes them (the user: "subways are not getting masked correctly... other tiles appear to not overlap with them, and other cover them entirely"). With the lattice alone drawn, at its own depth, the sprites compose exactly as in sprite mode. The original's lattice shapes are replaced and the pipes, subways and markers drawn over it as before. The lattice is shapes 305 to 318, ``0x131`` plus the terrain code (``$164A2``), emitted by the sweep as plain sprites rather than terrain; the GPU path classified a wrong range, 318 to 331, and only among terrain ops, so the pixel lattice was still drawn over the mesh's hairline (the user: "why do you still have the pixel wireframe showing underground?"). It is classified by shape now, whatever the op's flag, and skipped with the mesh on. ``--underground`` starts there.

A bridge approach, ``XBLD`` ``0x57``, stands on a water tile and is a water tile: its sprite draws the road and its own supports over the water (the user: "102,71 and 102,72 should both be underwater"). An earlier build filled the tile to the table because the original's map-edge stack there is a dirt column; that stack is the edge's business, not the tile's. The suspension spans and towers on the water are water tiles the same way. In the colour field a stream reads as a level deep, the sea's blue rather than the shallows' turquoise, since its table is its level and it has no bed of its own; colour only. The plain-sweep switch, a debug mode that draws the sweep's list in painter's order with no depth test, lives in the Renderer window.

**Water is a body.** In mesh mode every water tile's surface is a mesh face, flat at its table and shaded as the sprite decal was, with the same field, noise normals, Fresnel, foam and caustics in world coordinates; the decals are the sprite mode's. The shore is the terrain's own edge, crisp at any zoom, where before it was the decal's magnified pixel outline against the mesh (the user: "since the water is a body, I expect crisp edges"). A marina stands on the water: its pad is the surface itself, calm, no foam and no caustics under the boats. The query tool targets one grid cell: the ground diamond under the pointer at its own drawn altitude, found by iterating on the altitude, so every cell can be reached on its own (the user, 2 September 2026: "it needs to be able to target individual grids"; a build that read the sprites first, so a tall building answered for the cells it covered, made those cells unreachable and is gone). The highlight is the whole footprint the cell belongs to, as the original finds it: ``sim_footprint_origin``, the reconstruction's ``$763A``, gives the footprint's edge n and its north-east tile, so it covers rows oy to oy+n-1 and columns ox-n+1 to ox (the marina at Bay View's column 118, row 16 is the 3x3 with its north-east tile at column 118, row 14; the elevated 2x2 pieces pair an even row with an odd column). Its outline is drawn on the surface the mesh draws, each corner from its own corner tile through ``tile_top``, so a building's pad gives a flat diamond of n tiles and a lone cell follows its own plane; in the underground view the corners come from the ground drawn there, the seabed under water (the user: "when querying in underground mode, we should be highlighting the terrain, not the water"). The line is white over dark, so it reads on any ground as the original's inverting outline did, and the query window names the footprint's edge and north-east tile. ``arcology <assets> <city> --scroll x,y --pick wx,wy [--shot out.png]`` prints the pick, the footprint and the outline's window points, and with ``--shot`` writes the frame with the query window and the outline on it, for checking without a pointer.

**One ground field** (the user's rule of 1 September 2026: "the terrain mesh needs to agree with itself everywhere, THEN you add engineered walls/raises"). The field is the first rule above, and every pad, plane and wall stands on it without changing it. The layers of every cut are measured from the bed field, so they are continuous across shorelines and under every foundation; the glass carries the bed per vertex, so the cut is continuous across tiles where the bed steps; a water tile on a cut edge draws its surface as a mesh face shaded exactly as the decal shades it, so the water meets the cut in a straight line at any zoom instead of the decal's stair-stepped diamond edge against the straight face.

**Roads, rails and power lines as geometry** (the user, 2 September 2026: "a road renderer, which we can enable/disable like the other enhancements... real curved segments instead of the sharp diagonals we have today... the road width to remain constant"; then the joins, the crossings, the width and the details in turn). The reference for this work is the user's road system specification, reproduced whole as :doc:`appendix-road-spec`, since 2 September 2026 with its part 5 on railways; its feasibility against the save format is tabled on :doc:`future`, and what follows is what is built. With the mesh on, the R key, the View menu's Road mesh or ``--roads3d`` replaces the sprites of the three network families that share one fifteen-piece layout, power lines at ``XBLD`` ``0x0E``, roads at ``0x1D`` and rails at ``0x2C``, and of the six crossings ``0x43`` to ``0x48`` that carry two families on one tile, with geometry on the surface (``K_ROAD_ART``, classified by shape id; the tunnels ``0x3B`` to ``0x42``, the highways from ``0x49`` and the bridges keep their sprites). The crossings were read off every shipped city's neighbours rather than a table: ``0x43`` is a road east-west under a power line and ``0x44`` a road north-south under one, ``0x45`` a road east-west over a rail and ``0x46`` one north-south, ``0x47`` a rail east-west under a power line and ``0x48`` one north-south. An earlier table had ``0x44`` to ``0x46`` turned and lacked ``0x43`` and ``0x48``, so a power line stopped at every road it crossed and the crossing stayed a sprite among the geometry (the user: "you render powerlines correctly except over the road", Barcelona, column 88, row 23). With the road mesh on the traffic sprites and the train sprites stay off, since a pixel car on a modelled road is the wrong kind of thing (``K_CAR``, the stencilled sprites of ``$19004``; ``K_TRAIN``, shapes 374 to 378), and both are drawn as geometry instead (the user: "we need rendered train cars", "I still need rendered road cars too"). A train is one thing record per car, types 10 and 11, found through ``XTXT`` as the original finds them, each a turned box on the track for its direction, right-hand running as the specification's signalling assumes, along the axis of the rail piece under it and facing by the record's heading; the engine is type 10 and darker. The road cars move (the user: "cars are completely wrong and unmoving... and need to respect the lanes"). The mesh keeps the road network it lofted, every segment's stations with the band's height and direction, its class and its two nodes, and the traffic lives on it: each segment is seeded with as many cars as the original's rule would give sprites, a tile past traffic 0x55 one and past 0xAA two, capped at a car and a half per tile of length and 2,500 in all; each car runs along its segment at a tile or so a second, in the right-hand lane of its direction at the lane centre its class draws, an avenue's outer lane and for a third of them the inner, holds behind the car ahead in its lane, holds at the stop line while the signal on its arm is not green, the same phase and cycle the lamps draw, crosses the junction box to a random onward arm, and turns back at a dead end, a map edge or a carrier. The cars are rebuilt into a buffer of their own every frame and drawn after the mesh. A car is a body and a low cabin, 0.15 of a tile long and 0.065 wide, less than a pixel tall at the base zoom (the user, on two larger tries: "they need to be MUCH smaller", "the cars are still too huge"), painted by the car; a train car is a rigid box 0.42 of a tile long and 0.10 wide, on the chord between its two bogies 0.14 each side of its centre along the path (the user: "since when do trains curve??", to a car bent along the path, and "make the cars smaller", then "still too big", to cars of 0.85 and 0.6 that cut the inside of the art's one-tile bends and half circles, which are under any radius the specification's 5.4 allows a class). The trains move too (the user: "trains need to be tighter"): the mesh keeps the rail network as it keeps the road's, a run of consecutive records on adjacent tiles in the save is one train with the type-10 engine at its head, and the engine runs along its segment on the track to the right of its direction while every car trails it by arc length on a ring of the engine's own path, coupled 0.48 of a tile apart, at 2.4 to 3 tiles a second (the user: "they're slow af"), so a train follows a curve car by car and a reversal at a dead end makes the tail the head. Across a junction box a vehicle that turns, a train onto a T's branch or a car onto a side road, follows a curve tangent to both arms through the corner where the arms' lines meet, the junction's own curve, rather than the chord across the box; straight through it crosses on the chord. At a turnout the engine takes the straightest arm. The crossings' gates and flashers belong to the same per-frame buffer: an arm lowers over two seconds while any car of any train stands within eight tiles of the crossing along the line, three seconds of warning at the trains' speed and the second-train rule of 3.15, and rises over three when the line is clear, its flashers alternating whenever it is off its rest; the arm is a bar 0.02 of a tile wide in red and white stripes, clipped to the tiles it reaches across (it had been a hair of 0.006 with its stripe code in the channel the lamp material does not read, a white thread no zoom could show). While the flashers are on, every road car on the segment through the crossing stops with its front at the stop line, 4.5 m before the nearest rail, and the cars behind queue on it (the user: "they don't cause traffic to stop"); the crossing's place on the road network, its segment and the distance along it, is found once from the nearest station to its tile's centre. Every vehicle pitches with the grade, its ground read a half length ahead and behind (the user: "cars/trains need to incline too if they need to"); vehicles are objects, not the surface, and the checks leave them out. Every face of a vehicle is clipped to the tile grid as the road's are, each piece in the depth slot of the tile under it (the user: "train cars get masked off once in a while, like they flicker"): a car had carried the slot of the tile under its centre, and the part of it over the next tile toward the viewer lay under that tile's ground until the centre crossed, when the whole car stood up at once. Within its tile's slot a vehicle's depth follows its place along the tile's diagonal toward the viewer, a tenth of a slot across the tile: the depth is the painter's index, not distance, so two cars overlapping in one tile, on the inside of a tight bend, had been resolved by draw order and fought (the user: "z fighting between the train cars"). Which edges a piece joins is read once from the road art, the asphalt or a dash in the three-by-three around each edge's midpoint a tenth of the way in, and the other two families take the road piece at the same offset; a slope piece is straight along its slope, which the terrain code says. A road or rail is not drawn tile by tile but as segments, the specification's part 3.10 (the user: "you need to not render as tiles... treat the roadway as segments that render and join elegantly"). The network's nodes are its junction tiles, a piece of three or four links whatever its neighbours return, and its end tiles, whose piece has one link a neighbour returns; every other tile lies on one segment, and each segment is walked once from a node to the next node, through loops without a node too. A link counts only when the neighbour's piece links back, or when it leaves the map, where the road runs to the tile's edge: a piece whose art points at grass, a stub against the flat side of a T, a road bulldozed short, all end there at a butt end, as the original draws every such sprite as it is. A piece no neighbour joins is drawn on its own, a band across its tile. Before that rule a chain with no node at either end, a road from map edge to map edge or a stub cut short at both ends, was never walked and its tiles went undrawn, their sprites skipped and nothing in their place (the user: "missing tiles for no good reason"); a scan in the check below counts them, and across the 99 shipped cities and scenarios the count is nought. Its centreline is the polyline through its tiles' centres, from the side of the junction box it leaves to the side it reaches. That polyline is straightened: collinear points go, and a staircase, a run of three or more bends turning left, right, left with grid-aligned legs of at most three tiles between them, becomes one straight line, the exact midline of the two parallel lines its corners alternate between (the specification's 3.9), joined to the legs before and after where it crosses them, so a 45-degree staircase draws as a 45-degree road and a 2:1 staircase as a 2:1 road (the user: "roads should become a true diagonal if it warrants it"); the rule is explicit rather than a chord tolerance, because the corners of a staircase alternate between two parallel lines a tile-diagonal apart and any chord leaves half of them standing off it. The legs of a staircase are whole tiles and alternate a riser of one with runs alike of one to three, the 1:1, 2:1 and 3:1 stairs of the specification; a jog of two bends is two corners, and a zig-zag of three-tile legs both ways is corners too, since its midline would leave the road tiles (Barcelona's north edge). A run ends where a leg differs from the one two before it, so a stair that meets a straight through a level crossing and goes on as a stair is two stairs and a straight, not one irregular run left to the fillet (Barcelona's rail at column 105, rows 4 to 11, which had snaked through a dozen tight arcs); a run that would end after one period because its first inner leg is unlike the third yields to the run from the next corner when that one is longer (Toronto's rail at column 108, row 25: a two-tile leg into a 1:1 staircase had been taken as a 2:1 stair of one step joined to the staircase by a half-tile jog, an abrupt turn where the staircase should have begun a tile later); a rail's corners are then cut (the user, on the same line: "why can't it have a softer angle to reach its destination?"): a leg of two tiles or less between two longer legs whose lines meet on one of them, at a turn of sixty degrees or less, goes, its two corners replaced by that point, so the line down column 111 that turned west a tile and a half and then north-west bends once, forty-five degrees, onto the staircase's diagonal a tile and a half further down the column, and the rail tile at the old corner, bypassed, is allowed by the check for undrawn pieces when a neighbour carries the line; a join that would land more than three tiles from the run, a leg already straightened lying nearly along the midline, is refused, and so is one that would land past the end of the leg it joins, since the polyline would then double back on itself: Toronto's rail at column 92, row 113, a three-tile step and a one-tile jog taken as a 3:1 staircase whose midline met the one-tile leg after it half a tile past its corner, drew a hairpin in the middle of a diagonal, and 131 such hairpins stood across the shipped cities; refused, the corners stand and the 1:1 staircase they begin is found from the next corner. A join that lands on the corner it replaces is kept once, since a repeated point made the fillet degenerate and dropped the whole segment. Every bend that remains is filleted with an arc, its radius a tile, clamped so the tangent points stay on the legs: a lone corner's quarter circle, the gentler sweep where a diagonal meets the grid. Then one strip is lofted along the whole path by arc length, a cross-section every eighth of a tile on the straights and every twelfth on the arcs, the dashes and the crosswalks placed by the distance from the junction. Every face of the strip is clipped to the tile grid and each piece carries the painter's order of the tile under its own centroid: a quad that straddles two tiles had carried the order of the tile under its midpoint, and the later tile's ground was drawn over the part of the quad inside it, a wedge of grass cut into every arc and every diagonal at each tile boundary, the notches at the bends of the user's Barcelona screenshot that the field's teeth had not accounted for (Barcelona's rail at column 106, row 10; Oakland's bends); a face lying wholly in one tile takes that tile's order too, not its caller's. There is no join inside a segment, and a segment meets its junction box square on at the box's own width. The road's profile is, at each station, the highest ground the cross-section spans, centre and both edges, and a hair above it, with a station every eighth of a tile and one wherever the centreline or either edge of the band crosses a tile edge, found by bisection and read on both sides of the edge, so a crest at the edge between a rising and a falling tile, or a small wall the band crosses obliquely, is met at a station and never the underside of a chord; then the grade is capped at one level per tile of road, the original's slope pieces' own pitch, by raising stations and never lowering them, with the two ends pinned to their nodes. So the terrain never cuts through the road: a road along a slope lies on it, a road across one rides on its uphill edge, and a straightened diagonal crossing the unlevelled corner tiles beside its road tiles rides over their ground; wherever that lifts the road above the ground at an edge, a wall of coursed blocks runs from the road's edge down to the ground, the embankment the pads have (the user: "raise roadways if they're going to cut into the terrain... the clipping I'm talking about was on the diagonals"). A running maximum over half a tile was tried first and rejected: on a uniform slope it lifted the road above its own ramp and grew a wall down every hill. The profile is then filleted as the plan is (the specification's 3.10: crest and sag vertical curves, R_v 20 to 60 m; the user: "soften the transition so that the roads don't abruptly change angles... raising/lowering the road segments with engineered walls"): it is averaged over half a tile each side, which rounds every grade break into a curve a tile long, about a metre off the break for the art's one-level-per-tile grade; at a sag the road rises off the ground onto its embankment of blocks, at a crest it sinks into the ground behind a retaining wall of blocks from the ground down to its edge, facing in, in the embankment's own material so the watertight check leaves it out with the strip, and the ground inside the band is painted over by the road, which in the sweep's depth stands in front of its own tile's ground whatever its height. The ends keep their height, a junction box, a carrier or a cap on the ground, the rounding fading in over the half tile from each. A quad in a cut is flagged in its class, four and up, so the clipping check, which otherwise forbids ground over a road, passes it. The ground in a cut is dug out, not painted over (the user: "when you go INTO the terrain, you must allow it to bend as well... there is clipping from the terrain because it hasn't been dug out"): the loft records the outline in plan of every quad in a cut, consecutive quads on one line merged up to a tile and corners within three hundredths of a tile line snapped onto it, and after the networks are built every face of the surface, ground, bank or wall, is clipped against each outline touching it and the part inside is dropped, the retaining walls closing the sides. The clipping is by the outline's edge lines, so a face the line crosses is split where the face across the shared edge is not, a T-junction; after the dig the faces in and beside every touched tile are welded, vertices within half a millimetre of one another taking one position, since two outlines' lines cross an edge at "the same" point a fraction of a millimetre apart, and each face is then split at any vertex of another that lies inside one of its edges, until none does, so the mesh conforms again and the watertight check holds without allowance beyond the rims of the cuts themselves, which are open by design and walled; an odd edge that other edges on its line cover end to end is also accepted, and a sloping edge shorter than the check's plan quantum, collapsed to a vertical, is no span. Outlines shorter than three hundredths of a tile are not dug, since their pieces vanish under the same quantum and the road covers that hair of ground either way. The grade cap came from Bay View's hills (the user, 2 September 2026: "I see a ton of clipping, especially in bayview with roads winding up and down hills"): where a fillet climbed across a slope piece, the profile rose a level in under half a tile, and that near-vertical face, shaded by its own tilt, drew as a black patch the road seemed to vanish under. It was not the terrain: ``r_mesh_check_roads``, run by ``--mesh-check`` whenever ``--roads3d`` is on, samples every road face on a barycentric grid, strictly inside the face since a sample on an edge reads the tile across it, and counts the samples a terrain top face stands more than two hundredths of a level above, a fifth of a pixel at the base zoom; Bay View had sixteen tiles under a level and now has none; over the 99 shipped cities and scenarios, none has any. The same run counts every road, rail or power tile that no network face touches, so a piece the walk could not draw is a failure rather than a gap; the four ``mesh_watertight`` tests run with ``--roads3d`` and fail on the first of either. ``SC2K_CLIP_DUMP=1`` prints each penetrating sample with the faces over it and ``SC2K_TILE_DUMP=col,row`` every face on one tile. Asphalt and paving keep their colour on a slope, as the sprites' slope pieces do: a third of the shading follows the tilt. The embankment carries its own material, so the watertight check, which counts every wall of the surface, leaves it out with the strip. An end against open land ends at the tile's centre with a round cap of the band's width, whatever the road's class and whatever stands beside it (the user: "all dead end roads should have endcaps"; the specification's 3.10, step 11, keeps the turning head for a local road with open land around it and ends an avenue square, but a square end in the middle of a tile is a raw edge); an end against anything from ``XBLD`` ``0x3B`` up, a tunnel end, a highway, a bridge or a building, runs square to the tile's edge, as the original draws the straight piece whole and the carrier's sprite goes on from there (a build that capped every end put a turning head at the foot of every bridge). A rail always ends square. The underground view builds no road geometry. ``SC2K_ROAD_DUMP=1`` prints every segment's polyline after straightening. The road strip is 0.71 of a tile wide, one width in the world in every direction, the width the road tiles of a 1:1 staircase inscribe, tile over root two (the user: "they need to be max 0.71 of the tile size by my calculations"; the specification's 3.9, the FIT policy), and across it, from the crown out: the asphalt of the sprites' palette to 0.8, a curb, and the sidewalk, concrete slabs scored every half tile, as the band's outer fifth each side (the user: "missing sidewalks, curbs, boulevards"). Beyond the band the tile's own ground shows, the grass margins the sprites have; a build that paved every road tile to its edges under the band, one face per tile, made a sawtooth of slabs along every diagonal and, on a hillside, terraces of concrete stepping down the slope, and is gone. A junction is a box of the band's width with the sidewalk and curb along its free sides, and where two arms meet, a curb return, the sidewalk's corner rounded on a fillet of its own width; the box, its sidewalks, its returns and every end cap stand the hair above the ground the strips do, 0.03 of a level, since on the ground itself under arms a hair higher the oblique view had shown a line of grass along every side of a rail box. Its class follows the traffic, one class for the whole segment, the median of its tiles', so a centre line does not start and stop mid-block with each tile's count: a two-lane road with the sprites' light dashes, nine to the tile; an avenue, traffic 64 and over, with a double yellow centre line and a dashed lane line each side; a boulevard, 160 and over, with a planted median between curbs, which ends at the junction box, plain asphalt. Every line is the art's width, one pixel at the base zoom, never thinner than a device pixel (the user: "the stripes are much too wide") and never wider than a fixed fraction of the strip, since the screen derivative the width is taken from swells in the sliver triangles at an arc's ends. The oblique camera draws a road running toward it wider on screen than one running across it, as it draws everything else; a build that scaled the world width by direction to equalise the screen width was rejected as inconsistent and is gone. The crosswalks lie on the approach tiles, which have the room the junction tile lacks: a straight road leading into a junction gives its last fifth to a band of white bars across the asphalt, six to the width, with the solid stop line at the band's outer end (the user: "crosswalks and stuff too"). A junction's arms are controlled as the specification's 3.4 tables it, from the classes of the roads meeting there: four local legs get a two-way stop on the quieter axis, a T with a local stem a stop on the stem, a local against an avenue stops on the local legs, avenue against avenue is an all-way stop or a signal where the junction is busy, and anything against a boulevard is signalled; a stop-controlled arm gets a STOP sign at the driver's right behind the crosswalk, an uncontrolled leg no crosswalk and no stop bar, and the cars stand a second at a stop sign and go. Where an arm is signalled it gets a signal, as the sprites carry a light at every T and crossing (the user: "real ones... proper ones with poles and lights hanging down"), sized by the specification's part 6 at the road's scale of fifteen metres to the tile and eight to the level, as are the street lights (1.6, 6.4: on an avenue or boulevard a cobra-head luminaire every two tiles, staggered side to side, a pole on the sidewalk ten metres tall with a three-metre arm out over the road; a local road goes unlit, its post-tops a downtown's), the crossing masts, plaques, flasher bars, gate mechanisms and arms, whistle posts, second-train signs and block signals: a pole at the driver's right-hand corner of the box, a mast arm from its top out over the road to the centre line, and a three-lamp head hanging from the arm's end with its lamps facing the approaching traffic; the lamps run a twenty-second cycle on the junction's own phase (the specification's 3.4 timing, scaled to the sim): north-south arms green six seconds, amber two, then an all-red clearance of two before the east-west arms' green, then the swap. A railway is a double track, one track for each direction, since the original runs its trains on a single track in both directions and lets them pass through one another (the user: "there needs to be two tracks... the old renderer technically collides trains, that's always something I've wanted to fix"). It is sized against the road as the road is sized to the tile rather than to the sprite or to metres (the user: "the original art is not relevant, especially since we had to resize the roads"): one ballast strip 0.62 of a tile, about a road's width, the two tracks 0.27 of a tile apart, the specification's 4.0 m at fifteen metres to the tile, and on each track timber ties 2.6 m long at 600 mm, twenty-five to the tile, fading to their mean where they pass a pixel's period, and two rails at the 1435 mm gauge, a tenth of a tile, each a device pixel at least and drawn light, their polished heads seen from above, since dark rails on dark ties had merged into one line at the base zoom (the user: "I'm not seeing two rails"). It is bent and joined by the same rules; where it crosses a road, the crossing tiles ``0x45`` and ``0x46``, the crossing surface is the road's and only the four rails show through it, flush, drawn a hair above the asphalt, and the crossing is built as the specification's 3.15 draws it for a double-track mainline (the user: "why don't we have the proper signaling?", then a diagram of the crossing drawn from the specification alone: "I think you're missing a ton of stuff"): one surface of dark rubber panels across both tracks, the road's width and its sidewalks, with the rails alone showing through it; on each approach, at the driver's right, a mast with the crossbuck, a two-track plaque and a pair of red flashers, a counterweighted gate post beside it with a red-and-white striped arm, a stop line across the approach lane 4.5 m before the nearest rail, two fifths of a tile, and a second-train sign facing the end of each sidewalk; from a tile and a half out the approach's centre and lane lines are solid and a large X is stencilled in each lane a tile out. The gates are down and the flashers alternate while a train stands within three tiles along the line, and are raised and dark otherwise, since the save says where every train is. Median flashers wait on a boulevard with a raised median; a rail junction is built within its box as a junction of two double-track lines (the user: "train T crossing are incorrect", of three half strips run to the centre, whose branch rails and ties had crossed through the through track's): the through line runs across the box whole, the branch's inbound track, the right-hand one, curves right into the near through track, and its outbound track runs on across the near track, a diamond, and curves left into the far one, each curve a quarter circle of 0.177 of a tile, the largest the box allows, since the specification's turnout (5.4) takes two to four tiles the art does not give; a crossing is two whole strips, a diamond. The line is signalled as 5.6 has it, right-hand running: the track to the right of the walk carries traffic forward and its signals stand on its outer side facing back, the other track's on the other side facing forward; a colour-light block signal every ten tiles, an absolute signal a tile before each junction, a whistle post two tiles before each level crossing, and none on or beside a crossing. Each signal's aspect is the traffic's, lit each frame with the gates: red while any car of a train stands in the ten tiles ahead of it in the direction it governs, green otherwise, so a train drops the signals behind it to red as it passes and they clear as it goes; and the trains obey them, a train stopping a hair short of a red signal on its track and waiting for the block to clear, its own cars not counted against it, so a train never runs into the one ahead on its track. A power line is a pole at the tile's centre with a crossbar and a wire, sagging a little, to each joined edge's midpoint, where the neighbour's wire meets it; over a road or rail crossing there is no pole and the wire spans from edge to edge (the user: "the power lines over roads look bad since it's a sprite that does the work"). Every strip and prop samples its heights from the drawn surface at each vertex's world position, whichever tile holds it, and the vertex shader lifts them a fifth of a depth slot over the ground so they win over the ground and stay under the tile's sprites. They are decals and props on the surface, not the surface, and the watertight check leaves them out. Not yet built from the specification: control by class, lane assembly, the ENCROACH and THICK policies, furniture beyond the signals and poles, and moving cars. Sheet: ``out/closeups-roads.png``.

**Free rotation.** For inspection, the mesh turns freely about the point the view looks at: comma and period by fifteen degrees, the palette's rotate buttons by ninety, 0 back to the snap, ``--angle`` to start turned. The pivot is the grid point under the view's centre, found by the same screen-to-grid routine the query uses, and it is taken afresh on every turn (the user: "I also want rotations to be centered around the current view"; the first build turned about the map's centre, and the view swung away with every step). A pivot never moves when the grid turns about it, so the scroll is set to put its unturned canvas position at the centre, and from then on any angle leaves the centre in place: at Bay View, ``--pick`` at the window's centre returns column 104, row 72 at 0, 35, 90, 200 and 315 degrees alike. The grid rotates about the pivot before the oblique projection, so the same camera sees the terrain from any side; depth is then the rotated row plus column rather than the painter's index, every water surface is a mesh face, and the cut runs along all four edges. The sprites cannot turn, so each follows its tile instead: the tile's centre turns about the map's centre as the mesh's grid does, and the sprite moves by the same canvas offset, unturned, with the mesh's rotated depth at the tile's centre, three quarters of a tile nearer so it stands above its own ground and behind the tiles in front (the user: "pretty sure the game had a solution for this, and I'm pretty sure it was just showing the same sprite"; the original shows the same art at every one of its four rotations, and an earlier build hid every sprite while turned). The sprite pipelines take the mesh's camera block for it, one struct for every pipeline that places things on the canvas. The road pieces turn into loose diamonds, the price of unturned art; the silhouettes, cast on the unturned canvas, stay off while turned. The original's rotation rewrites every layer of the city and is not built.

The material reads the topology. Each vertex carries, besides its face's normal for the lighting, the smoothed height field's gradient and its curvature (the Laplacian: positive in a hollow, negative on a ridge), and the fragment samples the terrain field's third channel, a land tile's distance to the nearest water by the same chamfer transform the water uses. From these: slope, mostly from the smoothed gradient so the material grades across the facets instead of stepping at each one; aspect, how squarely the slope faces the sun; altitude; hollow and ridge; damp ground within three tiles of water; and a beach on the waterline half of any level tile next to water. Lush grass (0.30, 0.50, 0.18, its hue drifting with a slow noise) goes dry (0.52, 0.55, 0.26) by altitude above eight units, ridges and sun-facing flanks, and stays lush in damp ground and hollows, which also darken a little as if in shade; earth (0.50, 0.42, 0.24) shows through as the slope passes 0.15 and rock (0.47, 0.45, 0.41) past 0.55, sooner at altitude; sand (0.76, 0.70, 0.50) lies on the beach; a two-octave grain at 9 and 23 per tile covers everything. The field texture is now four bytes per tile: water's distance to land, depth, land's distance to water, and one spare.

Key ``g`` adds the grid the sprites carry: every ground diamond has a darker stair along its four edges, two pixels per row in the flat tile (index 107 on 104) and a subtler one on the slopes (103 on 102). That stair is a one-pixel line, two pixels per row being as thin as a 2:1 line gets, and neighbouring tiles overpaint the same edge pixels, so the mesh darkens the pixels within half a pixel of each tile edge, by the true screen-space gradient of the grid coordinates, strong on flat faces and subtle on slopes, and the line stays one pixel at every zoom. On the shared surface the lines of neighbouring tiles meet across every edge, where the sprites' outlines on a slope sit up on the raised face and break from the neighbour's.

The projection is the original's, stated as numbers, and one number in it is a trap. A ground sprite's rise is its full height, so its diamond occupies the th + 1 rows *above* the tile's origin row, the top vertex at ``sy - th - 1`` and the bottom row at ``sy - 1``. The mesh rhombus, th tall, is centred on that hexagon. Measured against the software rasteriser's land-art pixels on a 1280 by 800 frame of Charleston, the mesh leaves 1,894 of about 204,000 uncovered, the one-pixel top and bottom rows of the diamonds, spread evenly across the map.

.. admonition:: A tiling cannot show a shift
   :class: caution

   A check that compares the union of all flat-tile pixels with the union of all mesh pixels passes with the mesh a whole tile too low, because both tilings cover the plane. Compare against one tile's own pixels, or count the uncovered art.

.. admonition:: Depth is per tile, on purpose
   :class: caution

   A depth that also encodes the fragment's height is too fine for the rasteriser: one sixty-fourth of a tile slot out of 32,770 slots interpolates unreliably and breaks into diagonal slivers. The mesh sits in the middle of its tile's depth slot, sprites at the top of theirs, and tiles order each other by the slot.

The water shader
----------------

.. rubric:: ``sprite_water.frag`` · ``arcology --water3d`` · key ``y``

The water keeps the sprites. Every water and shore sprite, 270 to 290, is drawn where the sweep put it through one fragment shader with two switches. With both off it is the sprite as it is, and the frame is the software rasteriser's. With the water shader on, the pixels whose palette entry is water -- in that art indices 79, 130, 184 to 188 and 192 to 195, the strongly blue entries; the beach is 104 and 106 -- are replaced with a shaded surface, and with the mesh on the pixels that are not water, the sand rim, are dropped, so the mesh ground runs up to the water and the sprite's water is a decal on the tile: the tile is flat at the table and the sprite is drawn at the table, so the pixels land on the quad exactly. The shading keys on depth. ``ALTM`` carries a bed under every water tile, the ground in its low five bits under the table in bits 5 to 9, which is what the map edge's water column is drawn from; across the shipped cities the depth runs from zero to nine levels, and Manhattan's river is zero throughout. The app packs that depth and the distance from each water tile to the nearest land, by a chamfer transform, into a 128 by 128 four-channel texture the shader samples bilinearly (the third channel, the land's distance to water, feeds the ground material). A tile's texel is centred on the tile, so the lookup is the world position over 128 with no half-tile added: an earlier build added one, and the whole field, shallows and foam alike, sat half a tile to the north of every coast, which showed as shallows on one side of an island only. In that field the coast line lies at distance one half, the first water tile at one. The colour runs from a turquoise over a bed at the surface through a mid blue by about two levels to a deep blue-green by four and a half, the distance to land adding three tenths of a level per tile so a zero-depth river still reads as water away from its banks and a one-level shelf next to the shore, which is what the shipped islands have, reads as a shallow ring; foam breaks in the band from the coast line to half a tile out, torn by noise and breathing with time, with a fainter second line to a tile and a half; caustic webs brighten the shallows and fade with depth. The surface normal is a noise height field at three scales, two of them drifting, differentiated in the shader; a handful of sinusoids at this scale interferes into a lattice, so no wave is periodic (the Gerstner function is kept in the shader for a swell where a scene wants one, unused by default). The camera of a 2:1 view sits about 27 degrees above the horizon, so Schlick's Fresnel, a little exaggerated, reflects the sky into the surface as the ripples turn it away, with a broad sheen and sparse sun glitter from the sun over the viewer's shoulder. Nothing is displaced: the water is a decal. The surface is computed in world coordinates recovered from the tile's diamond, so it runs continuously from tile to tile like the ocean, and the sprite's outline and the water column at the map edge stay exactly where the art has them. The palette's animated runs cycle blues among blues, so the water mark survives the animation. The water shader and the terrain mesh are independent switches. ``SC2K_FIELD_DUMP=path`` in the environment writes the field as a binary PPM when the mesh is built, for checking a city's depths; ``SC2K_MESH_DUMP=row,col`` prints what the mesh made of one tile, its kind, corners and bed, and the mesh line reports the canvas origin and the tile metrics for aiming a ``--scroll``.

Running the game
----------------

.. code-block:: console

   cmake -S render -B build     # finds SDL3, or -DSC2K_FETCH_SDL3=ON
   cmake --build build
   build/arcology assets "$CITY"                     # play
   build/arcology assets "$CITY" --check out.png     # one frame, both ways
   build/arcology assets "$CITY" --run 240 --speed 4 # headless, reports the clock
   build/arcology assets "$CITY" --shot ui.png       # one frame with the interface on it
   build/arcology assets "$CITY" --theme assets/themes/classic7   # in a Kaleidoscope scheme
   build/arcology assets "$CITY" --sprites           # the original's sprites for the ground and water
   python3 tools/gpu_diff.py out.png out.png.soft.png diff.png          # where they differ

The simulation runs as the original's main loop runs it: a phase of the 25-phase clock when the speed's deadline passes, the movers every fifteen ticks, the palette runs every twelve and ninety (see the clock's own speed on the :doc:`mechanics` page). The terrain mesh and the water shader are the game's look and on by default; ``--sprites`` starts with the original's sprites for both, and the check and the headless run start there too, since the sprites are the software rasteriser's baseline. Keys 1 to 5 set the speed, space pauses, the arrows pan, plus and minus change the art set, ``t`` and ``y`` swap the terrain and the water between sprites and geometry, ``g`` draws the grid outline on the mesh, ``v`` cycles the data views, ``u`` shows the underground, and ``p`` writes a check of the current view.

Continuous zoom
~~~~~~~~~~~~~~~

The zoom is continuous, as the renderer brief's section 5 has it, from an eighth to four times the 32 px set. The three art sets are levels of detail across that range, each used where it is closest to native, the 8 px set below 0.354, the 16 px set to 0.707, the 32 px set above, the switch points being the geometric means, so no set is ever stretched more than about 1.41 times either way. The canvas is drawn at the window's own resolution: sprite positions are canvas pixels, the same numbers the software rasteriser paints at, and the camera alone maps them to the screen, scaled by the remaining factor times the pixel density, so a sprite magnifies by nearest, texel for texel at an integer factor, which keeps the software-identity check exact, while the terrain mesh and the water shade every screen pixel and stay crisp at any zoom (the user asked why the mesh was pixelated when zoomed: an earlier build drew the whole canvas at the set's native size and scaled it up). The resolve pass then maps one to one, applying the shadow rule and the sky; its texel-boundary filter remains for a fractional factor between canvas and screen, which no longer arises. Sprites at a fractional factor are nearest-sampled, which the brief warns can shimmer as the camera moves; the brief's filter for them needs the palette resolved to colours before sampling, and is not built. The wheel zooms about the pointer, twelve percent a notch; plus, minus and the palette's zoom buttons step by two; ``--zoomf 1.3`` starts at a factor. Not built: the brief's ten-percent crossfade at each switch, which needs the map drawn twice inside the band.

Sounds
~~~~~~

The effects are the original's: twenty-eight ``snd `` resources, 500 to 527, BullDoze, Error, WIND, PLOP, Explode, Click, POLICE, Looping Fire, Dozer, FireTruck, COPTER, FLOOD, BOOS, CHEERS, ZZap, three voices, Takeoff, Land, Siren2, Horns, Prison2, ScBell1, TrainB7.5, Shot1, Arco2 and Roar1, 8-bit mono at their own rates, which ``tools/snd.py`` decodes to ``assets/sounds`` from their sampled-sound headers (the fork also holds the music's seventeen instrument samples and nineteen MIDI files, with ``SONG``, ``SMOD`` and ``INST`` resources: a music system, not yet read). ``r_sound.c`` plays them through SDL's audio, one stream per playing sound, mixed by the device. Where the original plays each is not yet read out of the binary; the app plays them where they plainly belong: Click on a palette button, BullDoze under the bulldozer, Error for a tool not yet ported, the disasters' own (fire, flood, the shot for the riot, the siren for tornado, earthquake and hurricane, the roar for the monster, the mayday for the air crash, the explosion for the meltdown, the spill and the volcano), CHEERS on a promotion and BOOS on bankruptcy, and a building's own sound under the query tool, which is how the original lets a building be heard: the police, the fire station, the school bell, the prison, the arcology, the wind plant, the airport's takeoff, the seaport's ship, the roads' horns, the rail's train.

The interface
~~~~~~~~~~~~~

The interface is the original's, from its own resources, with Dear ImGui as the engine under it. ``tools/pict.py`` decodes the application's ``PICT`` resources, all seventy-three of them version 2 pictures made of packed pixel maps with their own colour tables, and ``tools/pict.py --atlas rsrc/sc2k.rsrc assets`` packs the interface's pictures into ``assets/ui.png`` with their rectangles in ``assets/ui.json``, the tool palette twice, the second time inverted for the pressed look. The palette is ``PICT`` 500 in a floating windoid, the striped title bar and close box of the original's mini-window definition drawn by hand, with the thirty-four buttons the help texts ``TEXT`` 1100 to 1133 enumerate as hit rectangles measured from the picture's own bevels: the light top and left edges, the dark bottom and right. The menu bar is the ``MENU`` resources title by title and item by item, File, Speed, Options, Disasters, Windows and Newspaper, with a View menu of ours at the end for the switches; items the port does not have yet are greyed. The resources list the Apple menu first, but that is the Mac's menu, not the game's, and it is not drawn; its one item, About SimCity 2000, waits for a home. The windows wear System 7 chrome, a striped title bar with the title in a white box and a close box at the left, white with a black line round them. The pointer with a tool selected acts on the tile under it: the bulldozer demolishes, the query opens the query window, the centre tool centres the view; the zoom buttons zoom, the demand button opens the indicator with its three bars from a centre line, the under-view toggle switches the underground view, and the window buttons open the windows. Everything else logs that it is not yet ported: the sub-tool menus behind the landscape, dispatch, power, water, bonus, road, rail, port and zone tools, the sign, rotation, the layer toggles, and the map, ordinances, industry, neighbours and newspaper windows, which in the original are hand-drawn ``NewCWindow`` s over pictures with their own hit-testing. The text is Chicago 12: the original draws its interface in the system's Chicago, which is not in its resources, so the game ships Chicago-Kare, Duane King's reproduction of Susan Kare's bitmap under the MIT licence (``assets/fonts/``, with the licence), whose outlines lie on a sixteen-pixel-per-em grid; drawn at sixteen pixels with no hinting and no anti-aliasing, which FreeType in the build provides, every pixel is the bitmap's. ChicagoFLF, Robin Casady's public-domain outline revival, stands in if it is absent, hinted at twelve pixels, which the user found not pixel-accurate; ImGui's own pixel font stands in after that. The windows the palette opens are the game's stand-ins in the original's chrome, not the original's windows. ``--shot`` writes a frame with the interface on it; the interface's draw list goes into the renderer's command buffer as an overlay pass after the resolve. Events go to ImGui first and the map ignores those it claims.

Kaleidoscope schemes
~~~~~~~~~~~~~~~~~~~~

The interface takes a Kaleidoscope 2.x scheme as its theme (the user's earmark of 1 September 2026, built the same day). A scheme is a resource fork, and it describes itself: its ResEdit templates say that a ``cicn`` colour icon is each element, the menu bar, a menu item, the selected item, the pull-down background, the active document window, the utility window, the scroll bars and their thumbs; that a ``cinf`` entry with the same id gives the corner size and side thickness the icon is stretched by, and which of its pixels give the background colour, the text colour and the embossing colour; and that a ``wnd#`` entry lists a window frame's parts as rectangles inside its icon, the close box, the zoom box, the collapse box and the one-pixel title tile, with the parts that make each side. ``tools/scheme.py`` reads a scheme (raw or AppleDouble, as an unarchiver writes it), decodes the colour icons with the mask as alpha, and writes a theme pack: ``theme.png`` with the elements packed, ``theme.json`` with their rectangles, their ``cinf`` and the colours read from the pixels it names, and the window parts, and ``theme.txt``, the same flat, for the game. ``arcology --theme assets/themes/classic7`` loads one. What it dresses: the menu bar is the scheme's element stretched over it, corners fixed, each edge the one-pixel strip beside its corners stretched along the edge, and the middle filled with the sampled background colour, never stretched, because the icon's centre pixels are the colour samples themselves, which as a band read as a line through the menu titles; the menus take the scheme's background and text colours; every window's title bar is the scheme's frame, its left part to the title tile, the tile stretched across, the right part anchored right, the title in the middle, the close box where the window definition puts it, and the palette's windoid the same from the utility window. Not yet: scroll bars, buttons, the patterns, the inactive states, the selected item's text colour, which ImGui draws in the one text colour, and the side lists' meaning, which the templates name but do not explain. A scheme carries no font: its templates, ``Colr``, ``cinf`` and ``wnd#``, are the whole of its format and name none, and neither of the two packed here holds a font resource; the fonts of the period, Chicago and Charcoal, were the system's, and the mass:werk archive offers its fonts as separate downloads under Goodies. Two packs are checked in, from N. Landsteiner's mass:werk archive at https://www.masswerk.at/schemes.php, Classic7 and the mass:werk default, their forks under ``rsrc/``; the schemes are © N. Landsteiner / mass:werk, free downloads.

What is not built
-----------------

A check of the mesh silhouette against the sprite masks beyond the flat tile, a material with more than one band, the polygon rasteriser for views off the four snaps, map rotation in the game (the original rewrites every layer, ``$3AECA``, and only the Python port exists), and an exact traffic stencil. Each is on the :doc:`future` page with its status.
